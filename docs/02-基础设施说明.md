# 基础设施说明

本文说明「建了什么、为什么这么建、怎么验证」。
现状检查的结论见 [`01-现状检查报告.md`](01-现状检查报告.md)，GitHub 功能映射见 [`03-GitHub功能清单.md`](03-GitHub功能清单.md)。

## 一、技术选型与理由

| 决策点 | 选择 | 理由 |
|---|---|---|
| 语言 | Python 3.11+（本机 3.13.14） | 与本机既有脚本体系一致；Actions 运行器原生支持；零运行时依赖即可完成全部基础能力 |
| 包管理 | `pyproject.toml` 单一配置源（hatchling） | 打包、ruff、pytest 配置集中一处，不再维护 `setup.py` / `setup.cfg` / `pytest.ini` 多份 |
| Lint + Format | **ruff** 单工具双职责 | 比 flake8+black+isort 三件套快一个数量级，配置少、CI 时间短 |
| 测试 | pytest（23 个用例） | 生态标准；`pythonpath = ["src"]` 让测试无需安装即可跑 |
| CI 平台 | GitHub Actions | 用户长期偏好：云端一律优先 GitHub |
| git 传输 | **仅 SSH**（`ssh.github.com:443`） | 本机 `github.com:443` 不可达，HTTPS git 直接失败；SSH over 443 稳定 |
| 仓库初始化 | REST API（`api.github.com`） | 本机 gh CLI 缺失且无管理员权限；api.github.com 直连可用 |
| 站点交付 | 单文件 HTML，无外部资源 | 与用户既有交付规范一致（离线、移动端、可打印、无 CDN 依赖） |

## 三、核心设计：一个入口托管 N 个任务

```
cloudhub run <task>
        │
        ├─ registry.load_builtin_tasks()   导入即注册
        ├─ get_task(name)                  取任务类，未知任务 → 退出码 2
        └─ task(Settings.from_env()).run() → TaskResult(ok, pushed, data)
                                            ok=False → 退出码 1
```

为什么要这样：定时任务一旦多起来，"一个任务一套脚本 + 一套 crontab" 会迅速失控。
把分发收在注册表里，新增任务的成本是 **加一个模块 + 加一个工作流触发项**，主循环永不改动。

`TaskResult.pushed` 是为幂等留的：任务内部用「任务名:北京日期」做幂等键，
已推送过就返回 `pushed=False`，上层据此判断是否需要补推。

## 四、环境变量与配置项

| 变量 | 默认 | 作用 |
|---|---|---|
| `CLOUDHUB_OUTPUT_DIR` | `output` | 产物目录（CI 里再上传为 Artifact） |
| `CLOUDHUB_LOG_LEVEL` | `INFO` | 日志级别 |
| `CLOUDHUB_CHANNEL` | `auto` | 推送通道（为后续邮件/企业微信双通道预留） |
| `CLOUDHUB_DRY_RUN` | 空 | 非空即演练模式，不落盘不发送 |
| `GITHUB_ACTIONS` / `GITHUB_REPOSITORY` / `GITHUB_SHA` / `GITHUB_RUN_ID` / `GITHUB_ACTOR` / `GITHUB_REF_NAME` / `GITHUB_SERVER_URL` / `GITHUB_EVENT_NAME` | 由运行器注入 | 自动映射为 `Settings.github`，任务里不必自己读环境 |

**密钥策略**：任何密钥只走 GitHub Secrets，绝不出现在 `Settings` 的明文快照里
（`cloudhub check` 打印的 JSON 不含任何凭据）。

## 五、工程规范

### 提交规范

Conventional Commits，`type(scope): subject`，可用 `.gitmessage` 模板：

```bash
git config commit.template .gitmessage     # 已在本仓库设置
```

完整规则见 `CONTRIBUTING.md` 第二节。

### 分支策略（trunk-based）

- `main` 唯一长期分支，永远可发布
- `feat/*` `fix/*` `chore/*` `hotfix/*` 短期分支，PR 后即删
- 合并方式统一 **Squash**，PR 标题即提交信息
- 发布用 SemVer tag `vX.Y.Z` 触发 Release

### 质量门

```bash
python scripts/dev.py all
```

等价于 CI 里的 `ruff check` + `ruff format --check` + `pytest` + `python -m build`。
**本地与云端跑的是同一套命令**，避免"本地过了云端挂"。

## 六、验证方式（可直接复制执行）

```bash
# 1. 环境
python scripts/preflight.py

# 2. CLI
.venv/Scripts/cloudhub.exe --version
.venv/Scripts/cloudhub.exe list
.venv/Scripts/cloudhub.exe check
.venv/Scripts/cloudhub.exe run hello            # 生成 output/hello.json
.venv/Scripts/cloudhub.exe run hello --dry-run  # 不落盘，验证幂等分支

# 3. 质量门（与 CI 一致）
python scripts/dev.py all

# 4. 构建产物
ls dist/          # cloudhub-0.1.0-py3-none-any.whl + .tar.gz
ls site.zip       # 站点包

# 5. git 状态
git log --oneline
git remote -v     # origin git@github.com:youzunzhang/cloud-hub.git

# 6. 推送后验证（仓库建好之后）
ssh -T git@github.com
git push -u origin main
```

## 七、已知限制

1. **HTTPS git 不可用** —— 任何 `https://github.com/...` 的 clone/push 都会失败，必须 SSH。
2. **Release 附件下载不可用** —— `objects.githubusercontent.com` 不可达；发布可以（云端完成），
   本机下载附件需走 `api.github.com/repos/.../releases/assets/{id}`（`Accept: application/octet-stream`）或代理。
3. **Pages 与私有仓库** —— Free 账号下私有仓库不支持 Pages。若坚持私有，Pages 通道要等 Pro，
   或把仓库改公开。
4. **定时任务漂移** —— GitHub `schedule` 在高峰期可能延迟数分钟到数十分钟；对秒级准点有要求的场景，
   需改用 `workflow_dispatch` + 外部触发（如 cron-job.org）。
5. **定时任务自动停用** —— 仓库 60 天无提交时，GitHub 会暂停 schedule 工作流。
6. **LICENSE 未定** —— 视仓库公开/私有再决定。
